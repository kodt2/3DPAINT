# ADR 0016: Caddy TLS-контур (LAN и production), доверенный прокси по фиксированному IP (шаг H)

- **Статус:** принято (2026-11-25, шаг H)

## Контекст

- Приложение жилое только за HTTP (Gateway на `127.0.0.1`, presigned S3 —
  http). Для доступа по локальной сети и для production нужен TLS.
- Требования человека (шаг H): профиль `https`, Caddy с **закреплённым
  тегом**, для LAN — внутренний сертификат, для production — Let's Encrypt;
  HSTS **только** в production; `X-Forwarded-For` доверять только прокси
  (Caddy); README с инструкцией по установке корневого сертификата;
  E2E-проверка в headless Chromium с CA самого Caddy (без установки в
  системный trust-store хоста); `make e2e` (plain HTTP) продолжает работать.
  Часть «открыть модель из Razor UI» (п.4) отменена человеком.
- Локальный недокоммиченный правка `infra/compose.yml` (публикация Gateway на
  `0.0.0.0`) **отклонена**: наружу публикуются только порты Caddy, адрес —
  `${BIND_ADDR}` (дефолт `127.0.0.1`).
- Gateway уже умеет доверять XFF только доверенным прокси
  (`KNOWN_PROXIES`/`KNOWN_NETWORKS`, ADR 0011 §6.2) и проверяет Origin/CSRF
  (ADR 0011 §6). Монолит уже умеет подписывать presigned URL по публичному
  эндпоинту S3 (`PUBLIC_S3_ENDPOINT`).

## Решение

### 1. Caddy как единственный наружный TLS-контур

`infra/compose.https.yml` (профиль `https`, включается отдельно от базового
стэка):

- образ **`caddy:2.11.9-alpine`** (закреплён точным тегом);
- Caddyfile генерируется на каждом старте
  `infra/caddy/entrypoint.sh` из переменных окружения (детерминированный
  файл, можно посмотреть: `docker compose ... exec caddy cat /config/Caddyfile`);
- именованный том `caddydata` (`/data`): **внутренний CA переживает
  пересоздание контейнера** — установленный на клиентах корневой сертификат
  остаётся валидным.

Публикуются **только порты Caddy**, и только на `${BIND_ADDR}`
(дефолт `127.0.0.1`):

| Порт контейнера | Назначение | Режим |
|---|---|---|
| `443` | сайт → `gateway:8080` | lan и prod |
| `9443` | S3 → `storage:9000` (Host и path сохранены — SigV4-подписи presigned URL продолжают валидироваться) | lan |
| `443` | S3 → `storage:9000` (SNI-роутинг по `S3_HOST`) | prod |
| `80` | ACME (HTTP-01) и редирект | prod |

Gateway и S3 сохраняют только loopback-порты; из сети наружу ничего, кроме
Caddy, не видно.

### 2. Режимы TLS (`TLS_MODE`)

- **`lan`** (дефолт): `tls internal` — CA, самоподписанный Caddy. **Без
  HSTS** (заголовок не отправляется; проверяется E2E). Клиенты один раз
  устанавливают корневой сертификат (README, раздел «HTTPS»).
- **`prod`**: Let's Encrypt (обязательный `ACME_EMAIL`), **HSTS включён**
  (`max-age=63072000; includeSubDomains`). Нужен публичный домен в
  `PUBLIC_ORIGIN`/`PUBLIC_S3_ENDPOINT` и доступность Caddy на `:80`/`:443`.
  В prod-режиме S3 живёт на том же `:443`, что и сайт, — роутинг по SNI
  (`MAIN_HOST` и `S3_HOST` — разные хосты).

В режиме `lan` сертификат покрывает только SNI-хост `MAIN_HOST`:
`PUBLIC_ORIGIN` и `S3_CORS_ORIGINS` содержат **только** `localhost`
(без `127.0.0.1` — для него TLS-хендшейк протекать не будет).

### 3. Доверенный прокси: точный IP, не подсеть

- Сеть `app-network` закреплена за подсетью `172.28.0.0/16`
  (`infra/compose.yml`, `ipam`) — иначе IP контейнеров непредсказуемы.
- Caddy закреплён за **`172.28.0.10`** (`ipv4_address` в
  `infra/compose.https.yml`).
- Gateway получает `KNOWN_PROXIES: 172.28.0.10` — **точный IP**, не CIDR.
  Причина: соединения с хоста через опубликованные порты приходят в Gateway
  с bridge-адреса `172.28.0.1` — при доверии всей подсети хост мог бы
  подделывать ключ rate limiting через `X-Forwarded-For`. Порт самого
  Gateway наружу не опубликован, поэтому из сети Caddy вообще нельзя
  обойти.

### 4. Найденные в шаге дефекты Gateway (исправлены, тесты)

1. **IPv4-mapped адреса.** Kestrel на .NET 10 представляет IPv4-пиров как
   IPv4-mapped IPv6 (`::ffff:172.28.0.10`), а точное сравнение
   `IPAddress`/`List.Contains` mapped-адрес не считает равным обычному IPv4 —
   `KNOWN_PROXIES` молча переставал работать для всех соединений сети.
   `TrustedProxyClientKeyResolver` теперь канонизирует адреса
   (`IsIPv4MappedToIPv6 → MapToIPv4`) и при построении ключа, и при
   сопоставлении с `KNOWN_PROXIES`, и при обходе XFF. 4 регрессионных теста.
2. **Часы rate limiting.** Дефолтный clock `SlidingWindowCounter` брал
   `Environment.TickCount64` (миллисекунды) как ticks (100-нс единицы): окно
   «60 секунд» фактически было ~7 дней, а на хостах с аптаймом меньше этого
   бакет залипал в закрытом состоянии до рестарта процесса (live-симптом:
   `429` с `Retry-After: 60` не снимался часами). Исправлено:
   `TickCount64 × TimeSpan.TicksPerMillisecond`. Латентный баг с Фазы 4 —
   тесты с фейковым clock его не ловили; добавлен регрессионный тест с
   реальными часами.

Тесты Gateway: 49 → **54**.

### 5. E2E: `make e2e-https`

Отдельный одноразовый стенд (собственный compose-проект и порты, живёт
параллельно с `make e2e`):

- полный прогон Playwright-сьюта **через Caddy** (сайт `https://localhost:18443`,
  S3 `https://localhost:19443`);
- новый `frontend/e2e/https-viewer.spec.ts`: Draco-куб реально рендерится по
  HTTPS, декодеры берутся с origin сайта (`/assets/decoders/**`, без CDN),
  presigned S3 — только `https://`, в консоли нет mixed-content/CORS/
  cert-ошибок, HSTS в lan-режиме **отсутствует**;
- доверие CA без установки в trust-store хоста:
  * Chromium — `--ignore-certificate-errors-spki-list` (SHA-256 от
    SubjectPublicKeyInfo). Caddy предъявляет цепочку [leaf, intermediate]
    (root не отправляется), поэтому в список идёт **intermediate** (root —
    для Node);
  * Node-запросы (Playwright `APIRequestContext`) — `NODE_EXTRA_CA_CERTS`
    (корневой сертификат, цепочка проверяется штатно);
- оба сертификата копируются из контейнера Caddy после первого
  TLS-хендшейка (внутренний CA материализуется лениво);
- после прогона стенд (включая тома) удаляется; plain `make e2e` не тронут —
  https-спека проскипится без `E2E_S3_HTTPS_URL`.

Результат шага: `make e2e-https` — **30/30**, `make e2e` — 29 passed +
1 skipped (https-спека).

## Последствия

- **LAN:** клиент один раз устанавливает корневой сертификат Caddy (инструкция
  в README); корневой сертификат стабилен между пересозданиями контейнера
  (том `caddydata`). Внутренний сертификат живёт 100 часов и обновляется
  Caddy автоматически — на клиентах это не отражается.
- **HSTS** появляется только в `TLS_MODE=prod` (требование человека).
- **Rate limiting** по-прежнему работает по IP клиента (XFF от Caddy);
  подделка XFF с хоста невозможна (см. §3).
- Фиксированный IP Caddy — жёсткая связь с конфигурацией Gateway: смена
  адреса обязана сопровождаться сменой `KNOWN_PROXIES` (закомментировано в
  compose-файлах).
- Prod-режим (Let's Encrypt) в шаге **не прогонялся live** (нужен публичный
  домен) — проверена только генерация Caddyfile и логика entrypoint.
- Старая локальная правка Gateway `0.0.0.0` не коммитилась и отброшена;
  наружная видимость — только Caddy.

## Альтернативы (отклонены)

- **Публиковать Gateway на `0.0.0.0` и ставить TLS в Kestrel** — пришлось бы
  управлять сертификатами в приложении и терять единую точку TLS для сайта и
  S3; наружу открывался бы лишний сервис.
- **Доверять всю подсеть `172.28.0.0/16` (`KNOWN_NETWORKS`)** — хост через
  bridge-адрес `172.28.0.1` попадает в подсеть и получает возможность
  подделывать ключ rate limiting.
- **Ставить корневой сертификат Caddy в trust-store хоста для E2E** —
  трогает системное состояние машины; SPKI-список Chromium + `NODE_EXTRA_CA_CERTS`
  ограничивают доверие конкретным стендом.
- **nginx вместо Caddy** — Caddy даёт автоматический `tls internal`,
  ACME из коробки и проще в генерации конфигурации из окружения.
