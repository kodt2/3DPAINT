# ADR 0015: Единый лимит загрузки MAX_UPLOAD_BYTES и сужение SPA-загрузки до GLB (шаг 3c.4)

- **Статус:** принято (2026-11-24, шаг 3c.4)

## Контекст

- Монолит хардкодил 500 MiB (Kestrel `MaxRequestBodySize`/`MultipartBodyLengthLimit`
  = 524 288 000 байт + приложение), а Gateway читал переменную
  `MAX_UPLOAD_BYTES` с дефолтом 100 MiB. Лимиты двух краёв не совпадали:
  файл 150 MiB умирал на Gateway «голым» 413, а 500-миБайтный лимит
  монолита был недостижим. Человек потребовал (решение, 2026-11-24):
  **одна переменная** `MAX_UPLOAD_BYTES` с дефолтом 100 MiB, читаемая и
  Gateway, и монолитом, — и отказ файла, превышающего лимит, в том числе
  на уровне монолита, если запрос дойдёт мимо Gateway.
- SPA (шаг 3c.4) добавляет экран загрузки на тот же multipart-эндпоинт
  монолита `POST /api/files/upload`. Клиенту нужны лимит и список
  разрешённых расширений — без хардкода.
- Вьюер (3c.3) понимает только GLB (ADR 0014); остальные форматы в
  библиотеке открываются только как «Просмотр 3D недоступен» + «Скачать».
  Старый Razor UI сохраняет полный whitelist (STL/OBJ/STEP/STP/GLB).
- Битый `.glb` раньше принимался с 200 (файл в S3, запись в БД), хотя
  вьюер такой файл показать не может.

## Решение

### 1. Одна переменная — два края

`MAX_UPLOAD_BYTES` (compose, дефолт 104857600 = 100 MiB) читают:

- **Gateway** (`services/gateway/Program.cs`): Kestrel
  `MaxRequestBodySize` + `MaxRequestBodySize` маршрутов `/api/**` и
  catch-all = `MAX_UPLOAD_BYTES + 1 MiB` (тот же envelope-запас: лимит
  применяется ко всему multipart-телу — файл + boundary/headers, поэтому
  файл ровно в лимит обязан пройти Gateway). Превышение → «голый» 413 от
  Gateway (без JSON) — клиент обрабатывает 413 как «превышен лимит»
  независимо от тела ответа.
- **Монолит** (`UploadOptions`, ADR 0015):
  - body-уровень: Kestrel `MaxRequestBodySize` и
    `FormOptions.MultipartBodyLengthLimit` = `MaxBytes + 1 MiB`
    (envelope-запас: boundary, headers, form-поля). Это жёсткий обрез —
    защита от раздувания памяти multipart-буфером (multipart
    монолита буферизуется в памяти, TD-13);
  - приложение: `FileStorageService.ValidateFile` сравнивает
    `file.Length` с `MaxBytes` → `413 ProblemDetails`
    `{"title":"File too large"}` — человекочитаемый ответ для файлов
    ровно до лимита+envelope.

Файл ровно в `MAX_UPLOAD_BYTES` проходит все проверки и принимается
(проверка приложения — строгое `file.Length > MAX_UPLOAD_BYTES`).
Файл выше лимита, но ниже body-лимитов, отклоняется приложением с
413 ProblemDetails; существенно больший — «голым» 413 на уровне тела.
E2E фиксирует оба края: прямой запрос к монолику (413 ProblemDetails)
и файл ровно в лимит через Gateway (200, envelope-запас).

### 2. Публичный `GET /api/config`

Ответ (без авторизации — данные не персональные и не секретные):

```json
{ "maxUploadBytes": 104857600, "allowedUploadExtensions": [".glb"] }
```

- `maxUploadBytes` — тот же `UploadOptions.MaxBytes`, что проверяет
  сервер (единый источник значения);
- `allowedUploadExtensions` — список, который принимает **SPA**
  (пока `[".glb"]`), константа `ConfigApiController`.

**Как расширить список:** изменить `AllowedUploadExtensions` в
`ConfigApiController` (+ тесты/конфигурация). Это действие осознанно
не автоматизируется: вьюер (3c.3) и обработка (Фаза 6) поддерживают
только GLB — расширение списка без поддержки вьюера/обработки даст
файлы, которые можно загрузить, но нельзя посмотреть/обработать.
Пока что список расширяется вместе с соответствующим шагом.

### 3. Проверка GLB (magic bytes) на общем upload-пути

`UserFilesController.Upload` вызывает `FileStorageService.ValidateFile`
(проверка имени/расширения/пустоты/размера), который для `.glb`
вызывает `ValidateGlbFile` — чтение первых 12 байт и требования:

- magic `glTF` (4 байта);
- версия 2 (little-endian uint32 = 2);
- длина контейнера (little-endian uint32, читается как int32) ≥ 12
  (мусорные/отрицательные значения отклоняются) и ≤ фактический размер
  файла (`file.Length`, `long` — сравнение без переполнения). Эффективный
  верхний предел длины — `MAX_UPLOAD_BYTES` (файлы крупнее не доходят
  до проверки).

Нарушение → `400 ProblemDetails`
`{"title":"Invalid GLB file","detail":"..."}` — до записи в S3 и БД.

Проверка стоит на **общем** эндпоинте, поэтому она действует и для
старого Razor UI. Это изменение поведения осознанное: битый `.glb`
больше не принимается (ранее — 200 + сироты в библиотеке). Старый UI
на 400 показывает общий текст «Ошибка загрузки файла» (читает поле
`message`, которого в ProblemDetails нет) — приемлемо для временного
UI, который остаётся до удаления (Фаза 3, конец).

### 4. Экран загрузки SPA (временный)

Временный экран на multipart-эндпоинт (ADR 0015): кнопка + drag&drop,
очередь до 2 файлов, XHR-прогресс, отмена/повтор, клиентская
валидация до сети (расширение, размер, пустота — по `/api/config`).
В Фазе 5 (Models Service + presigned, ADR 0003) экран заменяется;
новые серверные абстракции в монолит не вносятся.

## Последствия

- Лимит меняется одной переменной в compose; дефолт 100 MiB.
- «Голый» 413 от Gateway и JSON-413 от монолита — два разных ответа на
  одно нарушение; клиент трактует 413 одинаково.
- `GET /api/config` публичен: раскрывает величину лимита и список
  расширений SPA. Это не секрет (человек подтвердил: лимит не скрывается).
- Старый UI: клиентская подсказка в `home-dashboard.js` всё ещё говорит
  «до 500 MB» (текст не синхронизирован с лимитом) — косметика,
  сервер авторитетен (записано в TECH_DEBT).
- В Фазе 5 models-сервис получает свой лимит (та же переменная
  `MAX_UPLOAD_BYTES`), multipart-эндпоинт монолита удаляется вместе
  с монолитом.
