# ADR 0018: Auth Service — RS256/JWKS, ключи, refresh-схема, ротация refresh, lockout и стратегия тестирования на PostgreSQL (шаги 4.1, 4.2)

- **Статус:** принято (2026-11-26, шаги 4.1 и 4.2)

## Контекст

Шаг 4.1 создаёт отдельный Auth Service (`services/auth`, ASP.NET Core Web API на
.NET 10, ADR 0012) с ASP.NET Identity (PBKDF2), собственным PostgreSQL
(своя БД и свой пользователь), миграциями и OpenAPI. Он выпускает JWT
(RS256, 15 мин) по схеме ADR 0007: публичные ключи — по JWKS, остальные
сервисы и Gateway будут валидировать токен локально.

Отдельные решения, требующие фиксации:

1. **Ключи подписи.** ADR 0007 требует RS256 и JWKS, но не определяет, как
   хранятся приватные ключи и как устроена ротация. Ключи не могут лежать ни в
   образе, ни в git (запрет AGENTS.md §10), при этом dev-окружение должно
   подниматься «из коробки», а production — отказывать в старте без ключа.
2. **Тесты на PostgreSQL.** В проекте нет автотестов (TD-17); Auth — первый
   сервис, которому нужны интеграционные тесты против реальной СУБД.
   Testcontainers (вариант из плана Фазы 4) требует Docker-в-Docker в среде
   исполнения тестов; команда CI/локальная разработка в этом проекте —
   `docker compose` + Docker-образы SDK (`make test`, `make test-auth`), а не
   хостовый .NET-рантайм с доступом к Docker API из процесса тестов.
3. **Совместимость контракта.** До 4.2 фронтенд и Gateway ходят в Auth только
   через e2e-стенд (прямой порт); основной трафик `/api/auth/**` и `/api/me`
   остаётся на монолите. Контракты `register`/`login`/`logout`/`me` должны
   совпадать с монолитом, иначе смена маршрута Gateway на 4.2 сломает SPA.

## Решение

### 1. Ключи RS256: два файла, named volume, fail-fast в Production

- Ключ — PEM (PKCS#8, 2048 бит, `Jwt:RsaKeySize`). Два файла:
  `Jwt:CurrentKeyFile` (обязателен) и `Jwt:PreviousKeyFile` (опционален).
  `kid` в JWT и JWKS — **JWK Thumbprint (RFC 7638)**: base64url(SHA-256)
  канонического JSON `{"e":…,"kty":"RSA","n":…}`. Это и есть «отпечаток
  ключа» из требований шага.
- **Development:** if-не-существует — генерация. One-shot контейнер
  `auth-keygen` (`command: ["keygen"]`, идемпотентный `GenerateIfMissing`)
  создаёт оба ключа в named volume `auth-keys` (0600). При ручной перезаписи
  `ASPNETCORE_ENVIRONMENT=Development` сервис тоже сам генерирует текущий
  ключ в том же volume. В dev JWKS всегда отдаёт два ключа — путь ротации
  проверяем в dev-стенде без реального обмена ключами.
- **Production:** ключ **обязателен**. `RsaKeyStore.Load()` при отсутствии
  `current.pem` бросает `InvalidOperationException` **до старта HTTP-сервера**
  (fail-fast, проверено: контейнер падает с понятной ошибкой). Оператор
  предоставляет файл через volume/secret; предыдущий ключ — опционален, при
  отсутствии — warning (токены, выпущенные им, не валидируются — это и есть
  окно ротации).
- **Ротация (модель current + previous):** оператор кладёт новый ключ в
  `current.pem`, старый — в `previous.pem`, перезапускает сервис. `JwksService`
  публикует оба ключа (оба `use: sig`, `alg: RS256`), `TokenValidationParameters`
  принимает подпись любым из них; подписывает только `current`. После того как
  все 15-минутные токены, выпущенные старым ключом, истекли, файл
  `previous.pem` можно удалить.
- **Идентичность токена независима от монолита.** `AUTH_JWT_ISSUER` /
  `AUTH_JWT_AUDIENCE` (дефолты `3dpaint.auth` / `3dpaint`) — собственные
  переменные, задокументированы в `infra/env/.env.example` как независимые от
  монолитных `JWT_ISSUER` / `JWT_AUDIENCE`. Смешение не допускается: переходный
  период «cookie ИЛИ JWT» (ADR 0011) предполагает, что валидатор должен
  отличать легаси-токен монолита от токена Auth.
- `kid` в токенах Auth **не совпадает** с `kid` монолита (разные ключи),
  поэтому валидатор с JWKS-кэшем обоих издательств не путает ключи.

### 2. Refresh-токены (часть 4.1; ротация и lockout — 4.2)

- Opaque-токен (32 байта `RandomNumberGenerator`, base64url), **в БД только
  SHA-256 хэш** (колонка `TokenHash`), срок `RefreshTokenOptions` (дефолт
  7 дней). Схема `RefreshTokens` входит в миграцию 4.1 — таблица нужна сразу,
  чтобы 4.2 не менял схему.
- Выдаётся на логине как httpOnly cookie `rt` (`Secure`, `SameSite=Lax`,
  `Path=/api/auth`). `POST /api/auth/refresh` намеренно **не** реализован в
  4.1 (это 4.2: ротация, детект повторного использования, lockout, очистка
  просроченных) — до 4.2 access-токен живёт свои 15 минут и пользователь
  перелогинивается; SPA это не ломает (401 → экран логина).
- Access-токен — cookie `jwt` (`HttpOnly`, `Secure`, `SameSite=Lax`,
  `Path=/`), совпадает с монолитным `AuthCookie` (ADR 0011): браузер не
  хранит никаких токенов.
- Логин при неверном пароле или неизвестном логине — **один и тот же 401**
  `ProblemDetails` с `detail: "Неверный логин или пароль"` (без точки) —
  user-enum не раскрывается. Проверка пароля идёт через один и тот же
  `UserManager.CheckPasswordAsync`-путь для обоих случаев.
- Политика пароля (`PasswordPolicyOptions`, из `appsettings`): минимум 10
  символов + встроенный список из 100 распространённых паролей
  (`Security/CommonPasswords.cs`). Отказ — 400 `ValidationProblemDetails`
  с полем `Password`.

### 3. Компоновка: своя БД, one-shot миграции, без внешнего порта

- `auth-db`: отдельный PostgreSQL (отдельный volume, отдельный пользователь
  `auth`/БД `auth`); пароль — только из `AUTH_DB_PASSWORD` (в
  `infra/env/.env.example` с комментарием; в git только example-значение).
- Миграции и seed (роль `User` через `RoleSeeder`) выполняются **только**
  one-shot контейнером `auth-migrate` (`command: ["migrate"]`) с
  `depends_on: auth-db: service_healthy`. Сам сервис **не** применяет
  миграции при старте (AGENTS.md §5).
- Auth **не публикует портов** ни в основном compose, ни в production-профиле
  (проверяется `make check-prod`, п. 2b скрипта). Единственное исключение —
  e2e-стенд (`infra/compose.e2e.yml`), где порт опубликован для прямых
  интеграционных проверок Auth без Gateway-маршрута (маршрут
  `/api/auth/**` → Auth появится в 4.2).
- Один Dockerfile на `sdk:10.0`/`aspnet:10.0`, `ENTRYPOINT ["dotnet","Auth.dll"]`;
  compose-команды one-shot-контейнеров — только подкоманда (`["keygen"]`,
  `["migrate"]`), т.к. compose дописывает `command` к ENTRYPOINT.

### 4. Тестовая стратегия PostgreSQL (решение, требуемое планом)

**Выбрано: интеграционные тесты против одного общего PostgreSQL-контейнера в
отдельном compose-стенде (`infra/compose.auth-test.yml`), без Testcontainers.**

Обоснование:

1. **Среда.** Тесты .NET-сервисов в проекте исполняются в Docker-образе SDK
   (`make test-auth` = `docker run mcr.microsoft.com/dotnet/sdk:10.0 dotnet
   test`). Testcontainers внутри такого контейнера требует доступа к
   Docker API из-под контейнера (docker-in-docker или bind mount
   `/var/run/docker.sock`) — это новый класс привилегий и новая поверхность
   для поломки, ради чего Auth-тестам нужен бы только PostgreSQL.
2. **Достаточность.** Auth-тесты проверяют HTTP-контракт + поведение
   Identity/EF против реального PostgreSQL (реальные SQL, индексы,
   транзакции, `unique`-ограничения на логин). Интеграционный слой, ради
   которого Testcontainers был бы оправдан, здесь именно СУБД — и один
   общий контейнер её даёт в полную силу.
3. **Изоляция.** Стенд — отдельный compose-проект с собственным
   `app-network` (подсеть `172.31.0.0/16`, Caddy-IP `172.31.0.10` — не
   пересекается с основным стеком `172.28`, e2e `172.29`, e2e-https
   `172.30`), собственной `auth-test-db` (volume `auth-test-db-data`),
   собственными ключами (`auth-test-keys`). `make test-auth` поднимает стенд
   (`up -d --build`), ждёт health, запускает `dotnet test` с
   `ConnectionStrings__AuthConnection` на стенд и **всегда** роняет его
   (`down -v --remove-orphans`, даже при падении тестов) — после запуска не
   остаётся ни контейнеров, ни сетей, ни volumes (требование шага).
4. **Дешевизна и воспроизводимость.** Один `psql`-контейнер стартует за
   секунды; весь стенд — один `make test-auth`, результат детерминирован
   (свежая БД на каждый запуск).
5. **Почему не in-memory / EF InMemory.** ASP.NET Identity + EF Core
   используют SQL-специфику (серверная проверка уникальности, транзакции
   роли/пользователя); InMemory её не покрывает и даёт ложное чувство
   защищённости.

Ограничение, принятое осознанно: тесты не проверяют поведение при
перезаписи ключей вживую (это сценарий оператора, покрывается dev-стендом
рукой) и не дают изоляции «по тесту» (тесты в одном `ICollection` делят
одну БД и один приложение-инстанс; каждый тест регистрирует уникального
пользователя).

Интеграционный стенд e2e (`infra/compose.e2e.yml`) публикует прямой порт
Auth (`AUTH_E2E_PORT`, 18095) — это допущенное исключение (п. 3): Playwright
проходит реальный register/login через Auth в браузере, когда Gateway уже
маршрутизирует туда (после 4.2).

### 5. Совместимость контракта с монолитом

Сравнение сгенерированных типов (`npx openapi-typescript` на `swagger.json`
монолита и Auth):

| Контракт | Монолит | Auth 4.1 | Вердикт |
|---|---|---|---|
| `POST /api/auth/login` → 200/400/401 | `AuthUserDto` | `AuthUserDto` | совпадает |
| `POST /api/auth/register` → 201/400/409 | `RegisterRequest{login,password,fullName*,birthDate*}` | `RegisterRequest{login,password,fullName?,birthDate?}` | **совместимо**: сервер стал строже по паролю, но полнее — фронтенд шлёт оба поля всегда (регистрационная форма собирает fullName+birthDate), принимаются и сохраняются. В сгенерированном TS они становятся optional — на клиентский код не влияет (тип input в `register()` задан вручную). |
| `POST /api/auth/logout` → 204 | — | — | совпадает |
| `GET /api/me` → 200/401 | `AuthUserDto{login,fullName,birthDate}` | `AuthUserDto{id,login,fullName,birthDate}` | **совместимо**: добавлен только `id` (разрешено условием шага) |
| `ProblemDetails` / `ValidationProblemDetails` | есть | есть | совпадает |

Разница маршрутов: в `ARCHITECTURE.md` §7.2 написано `GET /api/auth/me`, но
реальный монолит и фронтенд используют **`GET /api/me`** — Auth реализует
`/api/me` (совместимость важнее; таблица ARCHITECTURE поправляется при
следующей правке доков).

### 6. Нюанс .NET 10: `AddIdentity` перехватывает default-схему аутентификации

**Найдено при отладке 4.1:** `builder.Services.AddIdentity(...)` в .NET 10
ставит `AuthenticationOptions.DefaultAuthenticateScheme =
"Identity.Application"` (cookie-схема). Стандартный `AuthenticationMiddleware`
подхватывает этот default и аутентифицирует **cookie-схемой Identity**, а не
`Bearer` — `UseAuthentication()` не трогает JWT из cookie `jwt`, и
`[Authorize]` отвечал 401 на валидный токен. В .NET 8 этого не наблюдалось
(монолит работает на cookie-аутентификации, Bearer там не подключался).

**Решение:** в Auth являно устанавливаем все три default-схемы на `Bearer`
(после `AddIdentity`):

```csharp
builder.Services
    .AddIdentity<AuthUser, IdentityRole>(...)
    .AddEntityFrameworkStores<AuthDbContext>()
    .AddAuthentication(options =>
    {
        options.DefaultScheme = JwtBearerDefaults.AuthenticationScheme;
        options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
        options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
    })
    .AddJwtBearer(...);
```

Это делает Auth устойчивым к будущим изменениям Identity (любое `Add*`
схемы больше не сможет незаметно сменить default). Тест
`Me_WithValidToken_Returns200` защищает от регрессии: до фикса он падал
401, после — 200.

### 7. Пастка base64url при тесте подмены JWT

Последний символ base64url-подписи может нести **меньше 6 бит данных**
(остаток от выравнивания до 4 символов). Замена последнего символа на другой
может не изменить ни одного бита реальной подписи — поддельный токен
окажется с **идентичной** подписью и валидируется (тест «подмена подписи →
401» ложно падал 200). Правило, зафиксированное в
`AuthApiTests.TamperSignature`: менять **полную 6-битовую группу в середине**
подписи (позиция `sigOffset + len/2`), а не последний символ.

### 8. Refresh-ротация, детект повторного использования, lockout (шаг 4.2)

**Модель семейства (family).** Каждый refresh-токен — строка семейства
`FamilyId` (GUID): логин создаёт семейство и первый токен, `POST
/api/auth/refresh` создаёт нового токена **в том же** семействе и атомарно
помечает старого (`ReplacedByHash` + `ReplacedAt` в одном `ExecuteUpdateAsync`
с условием `ReplacedAt IS NULL AND RevokedAt IS NULL AND ExpiresAt > now`;
побеждает тот, у кого affected rows = 1). Из N параллельных refresh с одним
token ровно один получает 200 — остальным 401 (тест: 8 параллельных
запросов, ровно один победитель).

**Повторное использование (reuse) vs дубликат.** Реплей уже
заменённого токена классифицируется по `ReplacedAt`:

- внутри grace-окна (`RefreshToken:ReuseGracePeriodSeconds`, дефолт 60 с)
  — это **дубликат** (двойной выстрел браузера/SPA): 401, семейство **не**
  ревакуется, легитимный новый токен продолжает работать;
- вне окна — это **кража**: всё семейство ревакуется (`RevokedAt` у всех
  токен семейства), 401, warning-лог содержит только id семейства и
  пользователя — **никогда** сам токен (требование шага).

Все провалы refresh (неизвестный/истёкший/ревакуенный/повторный/отсутствует
cookie) — **один и тот же** 401 `ProblemDetails` с
`detail: "Сессия истекла. Войдите снова."`: клиент не может отличить случай
по ответу.

**Lockout (решение по вариантам из шага).** ASP.NET Identity lockout:
`Lockout:MaxFailedAttempts=5`, `Lockout:LockoutMinutes=15` (из
`appsettings.json`, `AllowedForNewUsers=true`). **Выбран вариант «тот же
401 с тем же телом»**, а не 429 + `Retry-After`: посторонний наблюдатель не
должен отличать «аккаунт заблокирован» от «неверный пароль» по ответу —
429 сам по себе стал бы этим отличием и раскрыл бы факт успешной подбора
(attacker узнаёт, что логин существует и пароли добирались). Тело ответа при
lockout и при неверном пароле побайтово идентично (`detail:
"Неверный логин или пароль"`); проверено тестом: 5 неверных паролей + 6-й
запрос **с верным** паролем — тот же 401.

**Остаточный риск DoS (зафиксирован по требованию шага).** Зная чужой логин,
attacker может 5 неверными паролями заблокировать аккаунт на 15 минут —
дешево и без последствий для атакующего. Это **принятый остаточный риск**:
первая линия защиты — rate limiting по IP на Gateway (он же с 4.3 делает
login/register/refresh согласованным лимитом); lockout защищает пароль от
брутфорса, а не от DoS по логину. Альтернативы (задержка на ответе, captcha,
повышенный порог) отклонены как более сложные и не закрывающие риск лучше.

**Logout** теперь ревакует семейство на сервере (не только сбрасывает
cookies) — украденный ранее `rt` после logout пользователя нежив.

**Фоновая очистка.** `RefreshTokenCleanupWorker` (BackgroundService,
`PeriodicTimer`) раз в час (`RefreshToken:CleanupIntervalHours`) удаляет
мёртвые строки пакетами по `RefreshToken:CleanupBatchSize` (дефолт 500)
пока не кончатся: `RevokedAt IS NOT NULL OR ExpiresAt < now`. Заменённый,
но внутри grace-окна, токен **не** удаляется (он нужен для детекта
duplicate до истечения `ExpiresAt`). Каждый тик — в собственном DI scope;
сбой тика логируется и не убивает воркер (следующий тик повторит).

**Схема:** миграция `20261126213344_AddReplacedAtAndFamilyIndex` добавляет
`RefreshTokens.ReplacedAt` (timestamptz, nullable) и индекс
`IX_RefreshTokens_FamilyId` (семейство ищем по family при reuse/cleanup).

### 9. SPA: single-flight обработчик 401 (шаг 4.2)

`frontend/src/api/session.ts` подвешен на API-клиент через опцию `fetch`
(openapi-fetch 0.17). Каждый защищённый запрос, получивший 401:

1. **один** общий `POST /api/auth/refresh` на всех параллельных 401 (в-flight
   promise переиспользуется и сбрасывается после разрешения);
2. при успехе — исходный запрос повторяется **ровно один раз** из
   заранее сделанного `clone()` (тело первого запроса может быть
   уже потреблено); повтор идёт через «сырой» fetch, минуя обработчик,
   поэтому второй 401 не запускает новый круг;
3. при любом провале refresh — **один** редирект на `/spa/login` (latch).
   Редирект **пропускается**, если мы уже на `/spa/login` или
   `/spa/register`: обе страницы сами шлют `/api/me` (проверка
   «уже вошёл?»), и без этого пропуска refresh, падающий на монолите
   (см. п. 10), перезагружал бы страницу входа в вечном цикле;
4. `/api/auth/**` (login, register, refresh, logout) не перехватывается:
   401 там — неудачный логин, а не истёкшая сессия.

Пока монолит не знает `/api/auth/refresh` (см. п. 10), refresh отвечает
non-2xx и поведение SPA эквивалентно сегодняшнему «401 → экран логина»,
только с одним дополнительным запросом. Тесты: 5 Vitest (10 параллельных
401 → 1 refresh + 10 повторов; провал refresh → ровно 1 редирект; повтор с
401 — финален; non-401 не трогается; `/api/auth/**` не трогается) и E2E
`session.spec.ts` (неавторизованный `/spa/library` → `/spa/login`, страница
стабилизирована: refresh-запросов ≤ 2 и их число перестало расти — цикл
отсутствует).

### 10. Ограничения, принятые осознанно (шаг 4.2)

- **Access-токен не ревакуется досрочно.** Logout/reuse-detector ревокуют
  только refresh-семейство; access-токен живёт до своего истечения (≤ 15
  мин, `AUTH_JWT_EXPIRY_MINUTES`). В 4.3 Gateway/монолит будут валидировать
  JWT локально по JWKS — чёрного списка access-токенов нет и не планируется
  (цель: 15-минутное окно компрометации вместо 30-дневного, ADR 0007).
- **До 4.3 refresh «не работает» на реальном трафике:** Gateway всё ещё
  маршрутизирует `/api/**` на монолит, а монолит `/api/auth/refresh` не
  знает (ответ 403/404 — non-2xx). Это сознательное состояние: SPA-обработчик
  уже готов, и после 4.3 (маршрут + JWT-валидация) refresh заработает
  без изменения фронтенда. Тест `session.spec.ts` зафиксировал эквивалентное
  поведение (редирект на логин, без цикла).
- **Grace-окно 60 с — компромисс:** меньше — двойной выстрел браузера
  ревакует сессию; больше — украденный токен дольше выглядит как дубликат.
  Настроенно через `RefreshToken:ReuseGracePeriodSeconds`.
- **Lockout не сбрасывается «снаружи»**: нет админ-API на снятие lockout;
  аккаунт разблокируется сам через 15 минут (осознанно — админ-функции вне
  рамок шага).

### 11. Монолит: две схемы JWT и строковый владелец (шаг 4.3a, 2026-11-27)

Решения человека, 2026-11-27 (изменения к плану 4.3): миграции пользователей
монолит -> Auth **нет** (в проде пользователей нет; хэши несовместимы —
монолит: собственная схема `SHA-256(password + соль)`, 16-байтовая соль,
без растяжки, без ASP.NET Identity (CURRENT_STATE §4); Auth: ASP.NET
Identity (PBKDF2-HMAC-SHA512, 100 000 итераций, 16-байтовая соль — §12) —
пароли не переносятся), Gateway JWT
**не проверяет** (TD-31, Фаза 5),
`/.well-known/jwks.json` на Gateway **не добавляется** (монолит ходит в Auth
напрямую по внутренней сети).

- **Две JwtBearer-схемы в монолите.** `JwtRs256` (Auth, ключи по JWKS) и
  `Bearer` (легаси HS256, `JWT_SECRET`). Выбор схемы — по `alg` JOSE-заголовка
  cookie-токена (без base64-декода тела, `JwtTokenHeader`); токен, не похожий
  на RS256, валидируется как HS256. Валидация **не ослабляется**: подпись,
  issuer, audience, срок — обязательны для обеих схем. HS256-токены теперь тоже
  несут `iss`/`aud` (из уже существовавших `JWT_ISSUER`/`JWT_AUDIENCE`, которые
  до 4.3a не использовались) — старым токенам без claims осталось жить <=
  `JWT_EXPIRY_MINUTES`.
- **JWKS-клиент монолита (`JwksKeyProvider`):** ленивая загрузка (первый
  RS256-токен, не старт), кэш в памяти; Auth недоступен -> старт и
  `/api/health` работают, защищённые эндпоинты — **401 (не 500)** + warning;
  неизвестный `kid` -> повторный fetch не чаще раза в 30 с (`AuthJwks:
  RefreshThrottleSeconds`); сбой fetch не сбрасывает кэш (ключи из последнего
  успешного JWKS продолжают работать). `RequireHttpsMetadata` управляется
  `AuthJwks:RequireHttps` (дефолт false — внутренний адрес Auth; fail-fast в
  `Program.cs` при неверной комбинации), без хардкода. `ClockSkew` общий для
  обеих схем: `JWT_CLOCK_SKEW_SECONDS`, дефолт 30 с, тестовый стенд — 0.
- **Владелец файла — строка.** Миграция `20261127001848_UserFilesUserIdToText`:
  `"UserFiles".user_id` `integer` -> `text` (данные сохраняются как строки,
  `5` -> `'5'`), FK `FK_UserFiles_Users_user_id` снят. Владелец для RS256 —
  `sub` как строка **без обращения к БД** (`CurrentOwner`); для HS256 —
  прежний lookup login -> `"Users".id`, приведённый к строке. Owner-check в SQL
  без изменений: `WHERE id = @id AND user_id = @owner` (теперь строковое
  сравнение). `"Persons".user_id` остаётся `integer` до 4.3c.
- **id Auth — GUID (решение 4.3a.1, 2026-11-27).** Решение 4.3a использовать
  числовой `int` id Auth **отклонено** человеком: числовая строка могла
  совпасть с владельцем-легаси монолита (Auth-пользователь со `sub='4'` и
  старый файл `user_id='4'`), а последовательный `IdentityUser<int>` — не
  стабильная идентичность. С 4.3a.1: `AuthUser : IdentityUser<Guid>`,
  `IdentityRole<Guid>`, `RefreshToken.UserId : Guid`; ключ генерируется
  приложением (`Guid.CreateVersion7()`), `sub` в JWT — каноническая
  строка GUID в нижнем регистре. Каноническая строка GUID никогда не равна
  числовому владельцу-легаси (`'4'`) — совпадение исключено по
  построению (тест монолита: файл `user_id='4'` невидим любому Auth
  RS256-пользователю с GUID-`sub`). В проде данных Auth нет, поэтому
  начальная миграция пересоздана с нуля (`20261127125229_InitialCreate`,
  ключи `uuid`) — без цепочки `int -> Guid`. Локальный dev: том
  `auth-db-data` пересоздаётся (локальные dev-аккаунты Auth теряются —
  принято). Чистка осиротевших строк легаси — только 4.3c (по отдельной
  команде).
- **Миграция — one-shot.** `dotnet LoginAndReg.dll migrate` (минимальный хост,
  без JWT/JWKS/S3-валидации) + контейнер `monolith-migrate` в compose
  (`depends_on: db: service_healthy`, web ждёт `service_completed_successfully`);
  web-процесс мигрировать не может. У `db` добавлен healthcheck
  (`pg_isready`, паттерн `auth-db`) — one-shot с `restart: "no"` не должен
  гоняться с холодным Postgres (поймано на e2e-стенде: exit 139).
- **`gen:api` — два источника.** Gateway `/swagger` не маршрутизирует (3d.2:
  без catch-all, неизвестные пути — 404), поэтому в dev оба документа доступны
  по loopback-портам из `infra/compose.override.yml` (dev-only, 127.0.0.1:
  Auth `${AUTH_DEV_PORT:-18096}`, монолит `${WEB_DEV_PORT:-18097}`); e2e/https-
  стенды получают свои (Makefile: 18098/18099, 18100/18101). `frontend/scripts/
  gen-api.mjs` собирает единый документ: пути `/api/me` и `/api/auth/**` — из
  Auth, остальные — из монолита; `components.schemas` — монолит, затем Auth
  (при коллизии побеждает Auth). `npm run gen:api:check` сравнивает
  регенерацию с закоммиченным `schema.ts` (exit 1 при расхождении).
- **`schema.ts` после 4.3a/4.3a.1:** +`POST /api/auth/refresh`; `AuthUserDto`
  + опциональное `id?: string | null` (GUID-строка, с 4.3a.1; до 4.3a.1 было
  `id?: number`); остальные пути/схемы идентичны монолиту (проверено diff-ом
  после 4.3a: +50 строк, ничего не убрано).
- **Тесты монолита:** новый проект `legacy/monolith/tests` (.NET 8, xUnit,
  `WebApplicationFactory<Program>` — настоящий процесс монолита), одноразовый
  стенд `infra/compose.monolith-test.yml` (своя Postgres + SeaweedFS, как в
  dev — ADR 0009; миграция применяется в контейнере до `dotnet test`).
  22 теста: HS256-принятие/отклонения, RS256-принятие/отклонения (чужая
  подпись, issuer, audience, срок), JWKS-недоступность (401 не 500, старт и
  `/api/health` без Auth), троттлинг неизвестного `kid` (1 fetch / 30 с),
  owner из `sub` (IDOR-отказ, прямое чтение `user_id` из БД), миграция
  (scratch-БД: `5` -> `'5'`, тип `text`, FK снят). Запуск — `make test-monolith`
  (и в `make test`).

### 12. Хэширование паролей Auth: проверенные параметры .NET 10 (pre-check 4.3b, 2026-11-28)

Задача (из плана 4.3b): не полагаться на память — проверить, что Auth
хэширует пароли с солью и растяжкой, и зафиксировать реальные параметры
установленной версии.

**Факты (из кода и тестов, не из памяти):**

- Auth использует стандартный хэшер ASP.NET Identity (`PasswordHasher<T>`,
  shared framework .NET 10; отдельного пакета `Microsoft.AspNetCore.Identity`
  в 10.x нет — тип в `Microsoft.AspNetCore.App`). Приложение **нигде не
  переопределяет** `PasswordHasherOptions` (проверено поиском по коду и
  `appsettings.json`) → работают дефолты пакета.
- Параметры установленной версии (источник: `dotnet/aspnetcore`, тег
  `v10.0.0`, `src/Identity/Extensions.Core/src/PasswordHasher.cs` и
  `PasswordHasherOptions.cs`): режим **`IdentityV3`** (дефолт
  `CompatibilityMode`), PRF — **PBKDF2-HMAC-SHA512** (`KeyDerivationPrf.HMACSHA512`,
  значение enum 2; SHA1 = 0, SHA256 = 1), итераций — **100 000** (дефолт
  `IterationCount = 100_000`), соль — **16 байт (128 бит)**, случайная на
  пользователя, subkey — **32 байта (256 бит)**. Формат хранения (Base64,
  61 байт): `[0x01, prf U32 BE, iterCount U32 BE, saltLen U32 BE, salt,
  subkey]` — все U32 big-endian.
- Проверено в рантайме (проба .NET 10 + интеграционные тесты): дефолты
  действительно `IdentityV3`/100 000; два пользователя с одним паролем —
  **разные** `PasswordHash` (разные соли); записанный хэш валидируется
  `IPasswordHasher<AuthUser>`; маркер `0x01`, prf = 2, iter = 100 000,
  соль 16, subkey 32.
- Отношение к монолиту: **несовместимые схемы** (монолит — `SHA-256(password +
  соль)` без растяжки, §11/CURRENT_STATE §4) — пароли не переносятся
  (решение 4.3, пункт 1).
- Достаточность: 100 000 итераций PBKDF2-HMAC-SHA512 — завышенный дефолт
  .NET, но консервативный по меркам современных рекомендаций (OWASP
  рекомендует ≥ 600 000 итераций для SHA-256; SHA-512 дороже на итерацию,
  но эквивалент всё равно ниже). Итерации **вшиты в каждый хэш**, поэтому
  повышение `IterationCount` в будущем автоматически обновит все хэши при
  следующем успешном логине (`SuccessRehashNeeded`) — без миграции данных.
  В 4.3b параметры не меняются; вопрос «поднимать ли `IterationCount`» —
  отдельное решение человека (см. отчёт 4.3b, «Решения, ожидающие
  подтверждения»).

**Тесты (`PasswordHashTests`, запуск — `make test-auth`, всего 32 теста):**

1. Два пользователя с одним паролем → разные `PasswordHash` (соль различна);
   формат V3: 61 байт, маркер `0x01`, `prf = 2` (SHA512), `iterCount = 100 000`
   (равен дефолту `PasswordHasherOptions`), `saltLen = 16`, subkey 32;
   записанный хэш валидируется хэшером хоста.
2. Пароль отсутствует в телах всех ответов (register / login / `/api/me` /
   400 по политике).
3. Пароль отсутствует в логах: тест заменяет `ILoggerFactory` хоста
   (регистрацию от `UseSerilog()`) на `SerilogLoggerFactory` поверх логгера с
   захватывающим sink (`CapturingLogSink`) — DI-логгеры и
   `UseSerilogRequestLogging` пишут в sink; sink гарантированно не пуст
   (строка request-logging). Статические `Log.Information` (старт/cleanup)
   в sink не попадают — пароля там нет.

### 13. Переключение трафика на Auth (шаг 4.3b, 2026-12-01)

- **Gateway — единственный маршрут в Auth.** С 4.3b `/api/auth/**` и
  `/api/me` маршрутизируются Gateway в Auth (`Upstream:Auth`, свой кластер,
  order 0; остальные `/api/**` — монолит, order 1). Порт Auth не
  публикуется ни в одном стеке (ранее только E2E-стенд открывал его
  напрямую — с 4.3b стенд ходит через Gateway). Маршрутизация, refresh-
  лимит (30/мин, `RATE_LIMIT_REFRESH_REQUESTS_PER_MINUTE`) и
  Origin-проверка для `/api/auth/**` — в ADR 0011 §6.3. Старый
  `AuthApiController` монолита снаружи недостижим; удаление — 4.3c.
- **Test-only короткое время жизни токена.** `JwtOptions` получил
  необязательное `ExpirySeconds` (`Jwt__ExpirySeconds` / env
  `AUTH_JWT_EXPIRY_SECONDS`): при значении > 0 переопределяет
  `ExpiryMinutes` (дефолт 15 мин). Нужен для E2E-стенда `make e2e-short`
  (5-секундные токены + `JWT_CLOCK_SKEW_SECONDS=0` у монолита): там
  `short-token.spec.ts` гоняет реальный refresh-on-401 SPA через Gateway
  (один refresh, без редиректа на логин). В normal/production операции
  переменная пуста — поведение не меняется. Альтернатива (отдельный
  «test»-режим Auth) отклонена: одно число в конфиге, без веток кода.
- **Смена владельца аккаунтов (последствие, не решение).** Локальные dev-
  аккаунты монолита (34 записи в `"Users"`) после переключения не
  логинятся (Auth не знает их — пароли не переносятся, §12); 24 файла в
  `"UserFiles"` остаются осиротевшими со строковыми числовыми `user_id`
  (`'1'`, `'5'`, …) — в 4.3b **не удаляются** (чистка — 4.3c, только с
  отдельным подтверждением).

## Последствия

- **Плюс:** Auth автономен (своя БД, свои ключи, свои миграции), dev
  поднимается без действий оператора, prod без ключа не стартует (нет
  «тихо работающего» Auth с сгенерированным на лету ключом), JWKS всегда
  валиден для ротации (1-2 ключа), тесты — одна команда, без остатков.
- **Плюс:** контракт совпадает с монолитом → 4.2 (маршрут Gateway → Auth)
  не требует менять SPA.
- **Минус:** dev JWKS отдаёт два ключа с самого начала (виртуальная
  «ротация» сразу) — для dev неважно.
- **Минус:** access-токен не ревакуется досрочно (окно ≤ 15 мин, п. 10);
  до 4.3 refresh на реальном трафике отвечает non-2xx (п. 10) — поведение
  SPA при этом эквивалентно «401 → логин» (E2E `session.spec.ts`).
- **Риск (остаточный, п. 8):** lockout — DoS на известный логин (5 запросов
  = 15 мин недоступности); первая линия — Gateway IP rate limiting (4.3).
- **Минус:** тесты делят одну БД (изоляция «по коллекции», не «по тесту») —
  принято осознанно (п. 4).
- **Риск:** `DefaultAuthenticateScheme` — скрытое поведение Identity; при
  обновлении .NET 10.x нужно повторно прогонять `AuthApiTests` (они это
  поймают).
- **Риск:** окно ротации (15 мин) — валидатор должен держать оба JWKS-ключа;
  Gateway (4.2) и монолит (при переходе на JWKS) должны кешировать JWKS и
  обновлять при 401/истечении, а не на каждый запрос.

## Альтернативы (отклонены)

1. **Testcontainers для PostgreSQL в тестах** — отклонено: docker-in-docker /
   bind mount Docker socket ради одного `psql`; compose-стенд даёт тот же
   реальный PostgreSQL дешевле и без новых привилегий (п. 4).
2. **EF InMemory / SQLite для тестов** — отклонено: не покрывает SQL-специфику
   Identity (unique, транзакции).
3. **Один ключ без `previous`** — отклонено: условие шага требует два
   (current + previous) и модель ротации; JWKS с одним ключом не даёт
   бесшовной ротации.
4. **Генерация ключа в Production при отсутствии** — отклонено: тихий
   self-signed key в проде = потеря всех валидных токенов при перезапуске +
   невозможность аудитного ротирования; fail-fast безопаснее.
5. **`/api/auth/refresh` сразу в 4.1** — отклонено: условие шага относит
   refresh-ротацию, lockout и cleanup в 4.2; делать endpoint без ротации —
   ложное чувство завершённости.
6. **Маршрут Gateway → Auth в 4.1** — отклонено: условие шага; без ротации
   refresh и lockout переводить реальный трафик на Auth нельзя.
